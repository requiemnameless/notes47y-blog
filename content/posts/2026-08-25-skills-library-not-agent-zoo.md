為每個職能各建一個 Agent，聽起來很直覺。寫作的、檢查的、整理資料的，各有一個對應的角色。做的時候很順：每個都能單獨調教，出了問題也知道該看哪一個。事情還少的時候，這套幾乎不會痛。

## 動物園是怎麼長出來的

想像這樣過了一陣子。Agent 變成一長排，能力彼此重疊，規則寫在不同地方，改一個行為要記得改好幾處。有的早就沒人用，卻不敢刪，因為不確定別的流程還倚不倚靠它。要新增一件相近的事，最省事的做法往往是再複製一個舊的出來改名字。於是動物園又多一隻。這不是能力不夠，是治理先垮了。

## 把能力做成技能，而不是做成角色

另一條路，是把能力從「某個 Agent 身上」拆下來，做成可組合的技能。Agent 比較像承載的那一層：它負責開工作、讀規則、呼叫技能。真正「會做哪一件事」的，是技能本身——一段寫清楚的做法、適用範圍、怎樣算完成，必要時附上例子。同一個技能，不同場合都可以叫；改一處，所有用到它的地方一起更新。公開可見的技能機制，走的就是這個方向：能力是模組，不是某個角色的私產。

這跟把一套大系統拆成可重用模組是同一類想法。動物園的問題是耦合：每個 Agent 是一個黑盒子，能力帶不走，也共享不了。技能庫做的是解耦：能力跟角色分開，知識才沉得進一個可以盤點、可以更新的地方。要檢查「我們現在到底會做哪些事」，打開的是庫，不是一長串角色名單。

對使用的人來說，差別很實際。不必為每個新任務再造一個新的 Agent；先問這件事是不是已有技能能做，沒有再補一個技能，而不是再養一隻。需要同時寫作和檢查時，是把兩個技能一起叫出來，而不是再造一個「又會寫又會檢查」的新角色。要維護的清單也比較短：看的是庫裡有哪些能力、各自還準不準。過時的技能可以標註、改寫或下架，影響範圍清楚；過時的 Agent 常常不知道還有誰在叫它。

## 技能裡該寫什麼

技能要寫得好，關鍵往往不在工具，在把實際怎麼做這件事說清楚。誰最清楚那件事，誰就該能參與定義。寫進庫裡的不是「這個 Agent 叫什麼」，是「碰到這種情況，步驟是什麼、邊界在哪、怎樣算完成」。

少造角色，多沉澱技能。庫裡能點名的能力，才是真正管得動的部分。
